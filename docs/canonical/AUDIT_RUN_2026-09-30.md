**Date:** 2026-09-30

## 1. Executive result

The protocol worked as intended.

The repository is not merely “Blocks 1–4 exist.” The deeper audit exposes several different realities:

- Block 1 implementation has progressed beyond its older audit wording.
- Block 2 canonical purchase code exists, but legacy order authorities remain.
- Block 4 has a corrected canonical fulfillment state machine, but Android still contains competing/legacy delivery contracts.
- The canonical delivery flow exists in Functions, but the Android checkout does not yet execute the post-purchase delivery flow.
- Firestore rules still permit direct listing-field mutations that the canonical contract says must be server-owned.
- A payment/inventory flow gap exists for Swift Wallet.
- Reservation expiry creates a potential late-payment financial/inventory edge case that requires explicit policy and testing.
- The audit documents themselves can drift behind implementation and therefore must be audited as evidence, not treated as proof.

**Overall:** 🟡 Canonical core substantially implemented, but not yet authority-consolidated or flow-verified.

## 7. Critical Flow Finding — Swift Wallet

The canonical createPurchaseOrder path does this for Swift Wallet:

reserveInventory()
↓
deduct wallet balance
↓
create ledger entry
↓
order.status = CONFIRMED
order.paymentStatus = PAID
order.inventoryStatus = RESERVED

The code does not call commitInventory() for the wallet path.

The reservation remains ACTIVE while the order is already CONFIRMED/PAID.

The MoPay confirmation path contains the inventory commit logic, but the Swift Wallet path does not pass through that function.

### Consequence

The canonical purchase flow can reach:

PAID + CONFIRMED
+
INVENTORY = RESERVED
+
reservation = ACTIVE

instead of:

PAID + CONFIRMED
+
INVENTORY = COMMITTED
+
reservation = COMMITTED

**Classification:** 🔴 Flow/mutation defect requiring remediation before Blocks 2–3 can be accepted.

## 8. Critical Flow Finding — Reservation Expiry vs Late Payment

MoPay orders reserve inventory for 15 minutes.

The expiry path releases the reservation through releaseInventory() and marks the reservation released.

The MoPay success path later requires reservation.status == ACTIVE before committing inventory.

Therefore a late successful payment can encounter:

ORDER = RESERVED
RESERVATION = RELEASED
PAYMENT = SUCCESS

and fail to commit the inventory.

The repository needs an explicit business/financial policy for this race: reject/refund the late payment, extend the reservation, atomically reacquire valid inventory, or another documented mechanism.

**Classification:** 🟡/🔴 high-risk payment/inventory edge case.

## 13. Firestore Authority Audit

The repository's Firestore rules correctly block direct client creation of listings, orders, delivery requests, and delivery routes.

### Critical exception found

The listings update rule does not exclude every server-owned field.

It protects fields including sellerId, shopId, listingType, price, stock, and counters, but does not comprehensively protect status, isAvailable, shareSlug, publishedAt, viewCount, or shareCount.

The canonical contract explicitly says these are server-owned.

Therefore a direct Firestore client update can potentially bypass the callable Listing Engine for fields that the architecture says are authoritative.

**Classification:** 🔴 authority/security mismatch.

## Audit principle validated

> Audit the architecture. Then audit the flows. Then audit the mutations and state transitions. Then verify the consumers. Then test. Then audit the diff.

The test drive confirms that this gives Swift a materially deeper view of correctness than a file-by-file repository audit.
